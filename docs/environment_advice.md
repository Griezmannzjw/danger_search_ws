# Ubuntu 26.04 Distrobox 容器 GPU 加速方案失败总结报告

**日期**: 2026-08-05  
**项目**: SimEnv 仿真环境（Unitree A1 + ROS Noetic + Gazebo Classic）  
**目标**: 在 Distrobox 容器内使用 GPU 版 libtorch 加速控制器推理，解决运行时卡死问题


## 核心结论与建议

> **鉴于后续计划使用云电脑，强烈建议直接将 GPU 加速环境部署在云电脑上，停止在本地 Distrobox 容器内继续投入时间。**

### 🎯 行动路线图

| 阶段 | 行动 | 说明 |
|------|------|------|
| **立即（本周）** | 本地继续使用 CPU 版 libtorch，完成核心功能开发与调试 | 保持开发不中断，用无头模式排查卡死根因 |
| **部署（云电脑就绪后）** | 在云电脑上搭建完整 GPU 环境，迁移 SimEnv | 选择预装 CUDA + cuDNN 的镜像，一键解决依赖 |
| **验证与优化** | 在云电脑上测试 GPU 版 libtorch，对比性能与稳定性 | 确认无误后，逐步切换到 GPU 推理 |

### 📌 为什么云电脑是最佳选择？

- **依赖全预装**：云电脑/云 GPU 实例通常提供带 CUDA、cuDNN、NCCL、cuSPARSELt 的官方镜像，彻底避免手动找包的麻烦。
- **版本一致性**：可选择与 libtorch 匹配的 CUDA 版本（如 13.2），确保编译和运行稳定。
- **性能充足**：云电脑 GPU 显存通常 ≥ 16GB，远超本地 RTX 5060 Laptop 的 8GB，不再担心显存溢出导致驱动崩溃。
- **环境隔离**：与本地开发环境分离，互不干扰，且可随时按需开关，节约成本。

### ☁️ 云电脑选择与部署建议

**推荐服务商与配置**（按性价比排序）：

| 服务商 | 推荐 GPU 型号 | 显存 | 约时租（元） | 适合场景 |
|--------|--------------|------|-------------|----------|
| **AutoDL** | RTX 3090 / A4000 | 24GB / 16GB | 15-25 | 开发调试、中小规模推理 |
| **阿里云** | GPU 计算型 T4 / V100 | 16GB | 20-40 | 企业级稳定、长期使用 |
| **腾讯云** | GPU 计算型 T4 / V100 | 16GB | 18-35 | 国内访问快 |

**操作系统选择**：Ubuntu 20.04 LTS（与当前容器一致，迁移成本最低）

**部署步骤**（在云电脑上）：
1. 选用预装 **CUDA 13.2 + cuDNN 9 + NCCL** 的深度学习镜像。
2. 安装 ROS Noetic、Gazebo Classic、LCM 等依赖。
3. 克隆 SimEnv 代码，使用与本地相同的 CMake 配置，直接链接官方下载的 `libtorch-shared-with-deps-2.13.0+cu132`（依赖齐备，编译无阻）。
4. 运行仿真，验证 GPU 推理稳定性。

> **成本提示**：按每天使用 8 小时、每月 20 天计算，T4 实例月花费约 3200-6400 元，远低于自行购置 GPU 设备，且省去大量维护时间。

**备选方案**：如果不希望长期租用，也可使用本地 Docker 拉取 `nvidia/cuda:13.2-cudnn-devel-ubuntu20.04` 镜像，在宿主机直接运行（前提是宿主机驱动匹配），但鉴于宿主机为 26.04 且存在兼容性问题，仍推荐云电脑。

## 2. GPU 方案尝试历程（简述）

### 阶段一：libtorch 2.7.1+cu128（CUDA 12.8）
- 手动创建 `CUDA::nvToolsExt` 目标后编译通过，但运行 1-2 分钟卡死，导致桌面注销。
- **原因**：宿主机 CUDA 13.2 与预期 12.8 不兼容，运行时显存分配异常。

### 阶段二：libtorch 2.13.0+cu132（CUDA 13.2）
- 升级 CMake 至 3.29.3，链接时报大量 `undefined reference`，缺少 `libcusparseLt.so.0`、`libnccl.so.2`、`libnvshmem_host.so.3`。
- 这些库无法通过 apt 安装，需手动从 NVIDIA 官网注册下载。
- **最终结果**：因依赖链断裂，编译无法完成。


## 3. 失败根因分析

| 问题 | 说明 |
|------|------|
| **依赖库获取障碍** | cuSPARSELt、NCCL、NVSHMEM 无法通过 Ubuntu 20.04 默认源或 NVIDIA 公共源直接安装 |
| **CUDA 版本不匹配** | 宿主机 13.2 vs libtorch 12.8，运行时显存分配异常 |
| **显存不足** | 8GB VRAM 不足以支撑 Gazebo + 点云 + 神经网络推理，易触发驱动崩溃 |
| **容器限制** | Distrobox 无法完全透传所有 GPU 设备节点及 systemd 相关服务 |


## 4. 后续行动计划（基于云电脑）

| 阶段 | 时间 | 具体任务 |
|------|------|----------|
| **短期** | 本周 | 本地使用 CPU 版 libtorch，完成核心功能开发，用无头模式排查卡死根因（`GUI=false` 等） |
| **部署** | 云电脑就绪后 | ① 选购带 GPU 的云实例（推荐 AutoDL RTX 3090 / 阿里云 T4），选择 Ubuntu 20.04 + CUDA 13.2 + cuDNN 镜像；② 安装 ROS、Gazebo、依赖库；③ 下载 libtorch 2.13.0+cu132 并编译 SimEnv |
| **验证** | 部署后 1-2 天 | 运行仿真，对比 CPU vs GPU 推理性能与稳定性，调整参数 |
| **长期** | 后续迭代 | 优化资源配置（降低点云频率、减少楼层），根据需求决定是否长期使用云电脑，或迁移至 ROS 2 + Gazebo Garden |


## 5. 总结

| 维度 | 结论 |
|------|------|
| **当前状态** | CPU 版可用；GPU 版因依赖链与显存问题无法在本地 Distrobox 稳定部署 |
| **核心教训** | 容器内手动安装 GPU 版 libtorch 依赖复杂，且硬件资源不足，不宜继续 |
| **最终决策** | **采用云电脑作为 GPU 加速平台**，本地仅作 CPU 开发，云上完成 GPU 推理验证 |
| **推荐理由** | 预装环境节省时间、显存充足、可按需使用、成本可控 |
